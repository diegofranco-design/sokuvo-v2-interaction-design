01 — Jobs to be Done
What users are
trying to accomplish

JTBD maps motivation across six stages and three roles. Four layers per job: functional (the task), emotional (the state they want to reach or avoid), social (how they want to be perceived), and continuity (what they need to enable the next person in the chain).

→
These jobs are the ground truth for all interaction design decisions. Every pattern in the conversation map traces back to a job defined here. Stages marked ✦ are new in V2.
02 — Mental Model Flows
How the system
handles each pattern

Three interaction patterns run across all six stages. Each has a distinct shape: how the system responds, what it shows while processing, how the user interacts with the output, and how the loop closes.

→
These flows are the system perspective. The conversation map (section 04) translates them into the user perspective — what users see and do at each moment.
03 — JTBD × Conversation Design
Why conversational design
is different

Visual UI design organises space. Conversational design organises time. The mental models, tools, and artefacts are different.

The core difference

Visual UI
Organises space
User navigates between screens
Interface waits
Sitemap = hierarchy of pages
Wireframe = layout of a screen
Conversational UI (Sokuvo)
Organises time and state
User expresses intent in natural language
System responds in turns
Conversation map = graph of states
Message anatomy = structure of a turn

The four artefacts and what they answer

01
Jobs to be Done
Answers: What is the user trying to accomplish and why?
Maps motivation across six stages and three roles. The continuity job is unique to Sokuvo — one actor's output is always the next actor's input.
02
Mental Model Flows
Answers: How does the system behave for each interaction type?
Three patterns (Read/Analysis, Artifact Generation, Write/Mutation) with happy paths and error maps. The system perspective, not the user perspective.
03
Artifact State Model
Answers: What states can an artifact be in, and what can the user do in each?
Seven states (generating, draft, iterating, pending_approval, published, archived, blocked) with explicit transition rules and ownership boundaries.
04
Conversation Map
Answers: What does the user see turn by turn, and how do multiple roles coordinate?
Three roles in parallel, showing what each actor sees at each moment, how the system responds, and where coordination events connect the roles.

The new V2 actor: the evaluator

V2 introduces a fourth actor in the Define stage: the spec evaluator. It is not a user, not a conversational agent, and not a system step — it is an automated quality layer that produces a score, identifies gaps, and controls a gate.

The evaluator raises design questions that do not exist in V1: How does the PM experience a blocked state caused by an automated score? How does the Eng Lead calibrate annotation depth based on a score they did not produce? How does the Developer know which evaluator gaps are worth their attention? These questions are the open questions in section 05.

05a — Service Blueprint · Define
Define stage

The Define stage is the only stage where the interaction begins with a user action rather than an auto-trigger. PM initiates the spec, Sokuvo clarifies and generates a draft, the spec evaluator scores it, and both PM and Eng Lead must clear separate gates before the stage transitions to Plan.

Click any cell to see full detail.

05b — Service Blueprint · Plan
Plan stage

Plan is auto-triggered by the Define gate closure. Sokuvo reads the full approved spec and generates a task breakdown. The Eng Lead is the primary actor — they refine, annotate, and assign before the PM reviews. Two separate gates (PM product approval + Eng Lead technical sign-off) are required to transition to Build.

Click any cell to see full detail.

05c — Service Blueprint · Build
Build stage

Build is driven by the Developer with IDE context injected via MCP. Sokuvo is heavily backstage — assembling context, routing escalations, populating PR descriptions, and running the initial code review. The Eng Lead reviews PRs in two discrete steps: analysis always separate from posting.

Click any cell to see full detail.

05d — Service Blueprint · Test
Test stage

Test introduces the multi-pass evaluator as the primary actor. The agent generates tests from spec ACs, then three evaluator passes run sequentially — structural (cheap), functional (balanced), adversarial (frontier, conditional). Humans respond to evaluator output rather than initiating actions.

Click any cell to see full detail.

05e — Service Blueprint · Review
Review stage

Review assembles the delivery record and routes each output through trust classification before human review. PM and Eng Lead conduct parallel reviews from different angles — PM validates AC coverage, Eng Lead validates technical quality. Both must sign off before Ship.

Click any cell to see full detail.

05f — Service Blueprint · Ship
Ship stage

Ship is the most backstage-heavy stage — three consecutive columns with no human action before the Eng Lead reviews the changelog and PR. The PM's explicit deploy approval is the only irreversible human action in the entire delivery chain. On approval, a cascade of automated closures fires.
