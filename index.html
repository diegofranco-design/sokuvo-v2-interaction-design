01 — JTBD × Conversation Design
Why conversational design
is different

Visual UI design organises space. Conversational design organises time. The mental models, tools, and artefacts are different.

The core difference

Visual UI
Organises space
User navigates between screens
Interface waits
Sitemap = hierarchy of pages
Wireframe = layout of a screen
Conversational UI (Sokuvo)
Organises time and state
User expresses intent in natural language
System responds in turns
Conversation map = graph of states
Message anatomy = structure of a turn

The four artefacts and what they answer

01
Jobs to be Done
Answers: What is the user trying to accomplish and why?
Maps motivation across six stages and three roles. The continuity job is unique to Sokuvo — one actor's output is always the next actor's input.
02
Mental Model Flows
Answers: How does the system behave for each interaction type?
Three patterns (Read/Analysis, Artifact Generation, Write/Mutation) with happy paths and error maps. The system perspective, not the user perspective.
03
Artifact State Model
Answers: What states can an artifact be in, and what can the user do in each?
Seven states (generating, draft, iterating, pending_approval, published, archived, blocked) with explicit transition rules and ownership boundaries.
04
Conversation Map
Answers: What does the user see turn by turn, and how do multiple roles coordinate?
Three roles in parallel, showing what each actor sees at each moment, how the system responds, and where coordination events connect the roles.

The new V2 actor: the evaluator

V2 introduces a fourth actor in the Define stage: the spec evaluator. It is not a user, not a conversational agent, and not a system step — it is an automated quality layer that produces a score, identifies gaps, and controls a gate.

The evaluator raises design questions that do not exist in V1: How does the PM experience a blocked state caused by an automated score? How does the Eng Lead calibrate annotation depth based on a score they did not produce? How does the Developer know which evaluator gaps are worth their attention? These questions are the open questions in section 05.

04 — Artifact State Model
What can be done
depends on what state
something is in

Every artifact Sokuvo generates passes through a defined lifecycle. The state model establishes the canonical vocabulary, the transition rules, the ownership boundaries, and the open questions that every surface must answer before wireframing begins.

→
The state model is a prerequisite for the conversation map and the service blueprint. Without it, you cannot answer: what actions are available here? Who owns this object? What happens if the user navigates away? These questions are answered by state, not by screen.

Why a state model

Sokuvo generates artifacts — PRDs, epics, user stories, documentation — that exist across multiple surfaces and pass through multiple hands. Without a shared vocabulary for what state an artifact is in, each surface invents its own labels ("In progress," "Under review," "Done"), and the actions available to users become unpredictable.

The state model defines the seven canonical states, the seventeen transitions between them, who can trigger each transition, which bounded context owns the artifact in each state, and what design principles govern every state-aware interaction.

The seven states

`generating` Bounded context: Sokuvo
What it is
The system is producing the artifact section by section. The artifact does not yet exist as an editable object.
Surface
Slack (waiting state + stage labels) or Web editor (section-by-section stream with skeleton placeholders)
Actor
System
What the user can do
Watch generation progress only — cannot edit, publish, or cancel mid-stream.
`draft` Bounded context: Sokuvo
What it is
Generation is complete. The artifact exists as an editable object owned by Sokuvo. Not committed to any record system. Gaps are labeled, sources are cited.
Surface
Slack (inline, collapsed, with expand action) or Web editor (full split-view with TOC + sources panel)
Actor
PM · Eng Lead · Developer
What the user can do
Edit inline · Regenerate a section (diff preview) · Mark a gap · Copy · Export as .docx · Publish · Discard
`iterating` Bounded context: Sokuvo
What it is
The user requested a revision. The system is regenerating targeted sections while preserving the rest. Artifact remains owned by Sokuvo.
Surface
Web editor — targeted section regenerates inline with diff preview (new vs. prior). User accepts or rejects before state returns to draft.
Actor
System (executing)
What the user can do
Accept the regenerated version · Keep the prior edit — cannot publish while a section is regenerating.
Open question — Multi-cycle version control is undefined. If the user regenerates → edits → regenerates again, is the original draft recoverable? This must be resolved before the iteration UX is fully designed.
`pending_approval` Bounded context: Both — boundary state
What it is
The user has clicked Publish. The system has prepared the Confluence write and is waiting for explicit gate approval before committing. This is the boundary between the Artifact Generation and Write/Mutation patterns.
Surface
Web editor (publish gate modal with full preview) or Slack (preview card with Approve / Edit / Cancel)
Actor
PM · Eng Lead (not developers)
What the user can do
Approve the write · Edit fields before committing · Cancel (returns to draft cleanly — no half-committed state). Silence is never approval.
`published` Bounded context: Record system — Confluence owns it
What it is
The artifact has been successfully written to Confluence. Carries Sokuvo provenance metadata: "Generated by Sokuvo" footer, traced-from links, bidirectional traceability. The Sokuvo draft is no longer the canonical version.
Surface
Confluence is the destination. Slack and Web show a receipt card with a deep-link to the published page.
Actor
System + PM (who approved)
What the user can do
Open in Confluence · View in Sokuvo editor (read-only) · Request a new version (creates a new draft — does not overwrite the published page)
`archived` Bounded context: Sokuvo
What it is
The artifact is no longer active — project archived, superseded, or explicitly discarded. Preserved for audit trail but not surfaced in active views.
Surface
Not surfaced in active views. Accessible via audit trail or admin panel only.
Actor
PM (explicit discard) · System (project archival)
What the user can do
Restore to draft (if not yet published) · View version history
`blocked` Bounded context: Sokuvo
What it is
Generation or publish failed and cannot proceed automatically. Causes: empty retrieval, Confluence write failure, permission error, or quality floor breach where all critical sections are flagged as sparse.
Surface
Web editor or Slack — specific error shown, never a generic failure message. The error must carry enough information for the user to know what to do next.
Actor
System (failure detected)
What the user can do
Provide missing sources and retry · Resolve the permission issue · Retry the write · Accept gaps and override the quality floor
Open question — The quality floor threshold is undefined — the system cannot determine when sparse gaps are severe enough to block vs. warn. This state may be incorrectly triggered or never triggered until the threshold is specified.

Design principles

The artifact is always in exactly one state
No state overlaps. generating and draft are sequential. iterating always resolves back to draft. An artifact that is published is not also draft. The state model is exhaustive and mutually exclusive.
Sokuvo owns the artifact until it is published
In generating, draft, iterating, pending_approval, and blocked — the artifact belongs to Sokuvo. Only on published does ownership transfer to the record system. This determines which surface is the canonical source of truth at each state.
Publish is a bounded context crossing, not a button
Moving from pending_approval to published changes the artifact's nature — from a Sokuvo draft to a Confluence record with a different owner, different edit surface, and different traceability model. That crossing must be explicit in the UI, not silent.
Silence is never approval — applies to publish too
The same principle that governs Write/Mutation previews applies to the publish gate. The system waits for an explicit approval signal. The pending_approval state holds the artifact at the boundary until that signal arrives.
Blocked is an honest state, not a generic error
When the artifact cannot proceed, the system names the specific reason — empty retrieval, permission failure, quality floor breach. A generic "something went wrong" message is a failure of the honesty principle.
Published does not mean frozen
The user can request a new version after publishing. This creates a new draft — it does not overwrite the published Confluence page. The Sokuvo editor reflects Sokuvo's version history; Confluence reflects what was committed.

Open questions

OQ1Quality floor thresholdBlocks blocked state design
How many sparse sections make an artifact too broken to publish? Options: (a) Fixed count — more than N critical sections sparse; (b) Ratio — more than 50% of sections sparse; (c) Section-weight model — sparse Goals or Acceptance Criteria blocks publish; sparse Open Questions does not.
OQ2Multi-cycle version controlBlocks iterating state UX
What is the full undo model across multiple iteration cycles? The diff preview handles one regeneration cycle. If the user regenerates → edits → regenerates again, the current model is silent on whether prior states are recoverable.
OQ3Confluence versioningBlocks Write/Mutation flow
Does publishing always create a new Confluence page, or can it update an existing one? Currently confluence_create only creates. If the PM publishes a PRD, edits it in Confluence, then re-generates in Sokuvo — two Confluence pages exist for the same artifact.
OQ4Ownership after publishBlocks Web editor design
After publish, who owns the artifact — Sokuvo or Confluence? If someone edits the Confluence page directly, does Sokuvo know? This requires either a sync mechanism or an explicit out-of-sync signal in the Sokuvo editor.
OQ5Continuity job — handoff signalHighest — blocks all stage transitions
What signal does the next actor receive when an artifact is published? Does the Eng Lead receive a Slack notification? Does it appear in their morning_report? Is there a named handoff event? This is the Define → Plan stage transition and currently has no designed surface.

06a — Conversation Map · Plan
Plan stage
full conversation map

Auto-triggered when both Define gates clear. The Eng Lead is the primary actor — they refine, annotate, and assign. Two gates (PM product + Eng Lead technical) required before Build.

→
This is the narrative sequence — what happens turn by turn. For the grid view, see the Service Blueprint (05b). Click any moment to expand the detail panel.
System event — Plan Auto-Trigger
Both Define gates cleared (PM product approval + Eng Lead technical sign-off). Sokuvo reads the full published spec — goals, constraints, ACs, technical annotations, evaluator score — and begins auto-generating the task breakdown. No user action required.
The transition event mechanism is undefined — open question X1.
M1 Sokuvo Auto-Generates Task Breakdown ✶ Evaluator
Sokuvo Artifact Generation Web dashboard
Sokuvo reads the approved spec from Confluence and decomposes it into a task breakdown: one or more tickets per acceptance criterion, with model tier assignments (frontier / balanced / cheap), estimated dependencies, and sequencing. The breakdown is a draft — it has not been written to Jira yet.
Job: Plan should not start because someone decided to start it — it starts because the gate conditions were met.
M2 Engineering Lead Reviews Auto-Generated Breakdown
Eng Lead Read / Analysis Web dashboard · Slack
Eng Lead receives a notification that the breakdown is ready. Reviews: task scope per ticket, model tier assignments, dependency graph, AC-to-ticket coverage. Plan evaluator gap list pre-populated alongside the breakdown.
Job: Not inherit a breakdown that collapses technically because model tiers are wrong or dependencies are missing.
Model tier appropriateness criteria are undefined. No rubric exists for frontier vs. balanced vs. cheap assignment.
M3 Eng Lead Refines Breakdown + Architecture Context
Eng Lead Artifact Generation (iteration) Web dashboard
Eng Lead edits the breakdown directly: rewrites task descriptions with architecture context, adjusts model tier assignments, adds sequencing constraints, links tasks to ADRs or prior decisions. Each annotation is structured — not free text — so it feeds directly into the IDE context package for Build.
Job: Leave architecture intent in the task so the developer receives it in their IDE — not in a separate Confluence page they may not read.
System event — Context Persistence
Each Eng Lead annotation stored as structured JSON on the Jira ticket: architecture decision, relevant code modules, sequencing constraint, linked decisions. This is the primary content of the IDE context package delivered via MCP in Build.
M4 Eng Lead Assigns Tickets + Sets Dependency Graph
Eng Lead Write / Mutation Web dashboard · Jira
Eng Lead assigns each ticket to a developer, sets dependency structure as explicit Jira links (not inferred), and marks breakdown as ready for the plan evaluator. Dependencies set before evaluation so the evaluator can check for circular dependencies.
Job: Start Build with clear ownership and a dependency order that prevents developers from blocking each other.
System event — Plan Evaluator ✶ New V2
plan_evaluator runs three checks: (1) every AC maps to at least one ticket, (2) model tier assignments appropriate for task complexity, (3) dependencies complete and non-circular. Output: three coverage scores and a gap list. Surfaces gaps without blocking — Eng Lead decides whether to address before PM review.
M5 Eng Lead Reviews Evaluator Results ✶ Evaluator
Eng Lead Read / Analysis Web dashboard
Eng Lead sees plan evaluator output: coverage scores per dimension and a gap list. Decides whether to address gaps before forwarding to PM, or to forward with known gaps flagged. This is a judgment call — the evaluator does not block.
Job: Catch decomposition gaps before PM review — a spec AC with no ticket means a feature will not be built.
M6 PM Reviews Plan — Spec Traceability Check
PM Read / Analysis Web dashboard · Slack
PM sees the full task breakdown mapped to the original spec: every AC has at least one ticket, scope matches what was agreed, priorities correctly sequenced. Plan evaluator scores visible.
Job: Know the plan actually covers what the spec asked for — not discover a missing AC in week 3 of Build.
Side-by-side spec vs. plan view is a named requirement but has no workflow or surface.
M7 PM Approves Plan or Returns With Feedback
PM Write / Mutation Web dashboard · Slack
PM makes an explicit approval decision. If plan passes: approval recorded and batch ticket creation begins. If gaps: PM returns to Eng Lead with section-linked feedback. Returned plans re-enter at M3.
Job: Own the product decision that this plan is correct before Build starts.
Gate — PM Plan Gate
PM approval fires the ApprovalGate for batch ticket creation. Preview shows: ticket titles, AC mapping, model tier, assignee. Write executes only on explicit PM confirmation.
Batch pattern: review-each vs. approve-all threshold is undefined (X8).
System event — Batch jira_create
On PM confirmation, batch jira_create executes: parent records first, children linked. Audit trail entry written per ticket. Dependency graph preserved in Jira as linked ticket structure.
M8 Developer Reviews Assigned Tickets + Confirms Readiness
Developer Read / Analysis Slack · Web · Cursor/IDE
Developer receives Slack notification with assigned tickets. Reviews scope, AC, architecture context. Can ask questions via Sokuvo — deep_research answers from context, unresolvable questions route to Eng Lead.
Job: Know what you are building and why before writing a single line of code.
The ready-to-build confirmation is a named intent but has no workflow or surface.
M9 Eng Lead Technical Sign-Off on Plan
Eng Lead Gate (outside Sokuvo) Slack · Web (no dedicated surface)
Eng Lead reviews the final plan and gives technical sign-off — architecture decisions complete, model tiers correct, dependencies sound. This is the second gate required for Plan → Build.
Job: Not ship a plan that collapses technically in the first week of Build.
Eng Lead approval surface is the most repeated gap across the delivery chain — appears in Define and Plan consecutively (X1).
Gate — Plan Dual Gate
Three conditions: (1) PM product approval recorded, (2) Eng Lead technical sign-off recorded, (3) batch jira_create complete. All three must pass.
Eng Lead approval has no designed surface — same gap as Define.
System event — Plan → Build Stage Transition
Both gates cleared. Sokuvo pre-assembles the IDE context package per ticket: spec section, AC, Eng Lead architecture notes, relevant code modules, coding standards, prior PR review feedback. This is the context waiting in the developer’s IDE when they open their first ticket.

Build stage
full conversation map

Developer-driven with IDE context via MCP. Sokuvo is heavily backstage — assembling context, routing escalations, populating PR descriptions, running initial code review. The Build → Test transition fires on PR merge.

→
Build is the most IDE-centric stage. Most moments happen in Cursor, not Slack. For the grid view, see Service Blueprint (05c).
System event — IDE Context Package Assembly
Sokuvo assembles the context package per ticket: linked spec section, AC, Eng Lead architecture notes, relevant code modules, coding standards. Pre-assembled proactively to meet the 15-second SLA from ticket open.
Pre-assembly at stage transition vs. on-demand: if pre-assembled, context may be stale when the developer starts hours or days later.
M1 Developer Opens Task in Cursor
Developer Read / Analysis Slack · Cursor/IDE
Developer receives a Slack notification that their task is ready. Opens the ticket in Cursor. The pre-assembled context package is already in the IDE sidebar — spec section, AC checklist, Eng Lead architecture notes.
Job: Start building with all the context you need — not spend 20 minutes piecing it together.
If the developer starts hours or days after pre-assembly, context may be stale. 15-second SLA is the constraint for on-demand.
M2 Developer Implements With Project-Aware AI
Developer Read / Analysis (continuous) Cursor/IDE
Developer builds with Sokuvo context active. The AI assistant knows spec intent, AC, architecture decisions, and coding standards. deep_research available inline for codebase questions. Escalation available for blockers.
Job: Write code that fits the spec intent — not code that passes tests but violates the original requirement.
M3 Developer Flags Blocker + Escalates From IDE
Developer Pattern B + Write / Mutation Cursor/IDE · Slack
Developer encounters a gap — ambiguous AC, architecture conflict, or out-of-scope request. Escalates from the IDE. Sokuvo classifies as product decision (→ PM) or architecture decision (→ Eng Lead) and routes with full context.
Job: Unblock yourself without interrupting the wrong person with an incomplete description.
System event — Escalation Classification + Routing
Sokuvo reads task context, spec section, and developer’s question. Classifies: product decision → PM, architecture decision → Eng Lead. Context bundle assembled automatically. 15-second SLA for routing confirmation.
M3a PM Responds to Product Escalation
PM Read → Write / Mutation Slack · Web dashboard
PM reviews escalation bundle and responds with a specific, bounded decision. Decision captured and written to task context, project memory, and audit trail.
Job: Make a scoped decision that unblocks the developer — not create more ambiguity.
M3b Eng Lead Responds to Technical Escalation
Eng Lead Read → Write / Mutation Slack · Web dashboard
Eng Lead reviews escalation with full context: developer’s question, relevant code module, spec section. Writes an architecture decision. Decision written to Jira task context, project memory, audit trail. IDE context updated immediately.
Job: Make a bounded architecture decision that reaches the developer in their IDE — not a Slack thread that gets lost.
System event — Decision Persistence
PM or Eng Lead decision written to three destinations: (1) Jira task context field (visible in IDE), (2) project memory in PostgreSQL, (3) audit trail (immutable). IDE MCP context package updated immediately.
M4 Developer Creates PR — Auto-Linked to Spec + Decisions
Developer Write / Mutation (automated) GitHub · Jira · Slack
Developer opens a PR. Sokuvo reads the diff via GitHub webhook and auto-populates the description: AC checklist, architecture decisions applied, key Build decisions, Jira link. Developer does not write the PR description from scratch.
Job: Create a PR that tells the reviewer everything — not one that leaves them guessing.
System event — Automated Code Review
code_review runs the first automated pass: AC coverage check and architectural pattern compliance. Posted to GitHub as a labeled “Sokuvo Review Summary” — not inline comments. The Eng Lead’s manual review starts from this baseline.
M5 Eng Lead Reviews PR — Analysis Step
Eng Lead Read / Analysis GitHub · Web dashboard
Eng Lead reviews PR against spec AC and architecture decisions. This is the analysis step — does not post comments yet. Two-step separation (analysis, then posting) is deliberate.
Job: Review against spec and architecture decisions — not just code style.
GitHub PR UX does not enforce the two-step separation natively. How does Sokuvo surface the separation without adding friction?
M6 Eng Lead Posts Review — Approves or Requests Changes
Eng Lead Write / Mutation GitHub · Slack · Jira
After analysis, the Eng Lead posts the review. Approves or requests changes — all feedback linked to specific ACs, not free-text. Audit trail entry written: reviewer, ACs verified, decision.
Job: Give feedback tied to spec requirements — so the developer knows exactly what to fix and why.
M7 Developer Addresses Feedback + Pushes Update
Developer Write / Mutation → Read (re-review) Cursor/IDE · GitHub · Slack
Developer addresses AC-linked feedback, pushes update. Sokuvo re-runs targeted automated review — only new issues or previously flagged issues still unresolved. Does not re-review items that passed.
Job: Close the review loop by fixing the right things — not addressing style while missing AC failures.
System event — Build → Test Stage Transition
PR merged. Sokuvo triggers test generation. Transition fires on merge — not on a manual trigger. All Build stage decisions, architecture context, and review history are available to the Test agent.
06c — Conversation Map · Test
Test stage
full conversation map

Auto-triggered by PR merge. The multi-pass evaluator is the primary actor. Humans respond to evaluator output rather than initiating. Five gate conditions must pass before Test → Review.

→
Test is the most evaluator-heavy stage. Three passes run in sequence: structural (cheap), functional (balanced), adversarial (frontier, conditional). For the grid view, see Service Blueprint (05d).
System event — Test Suite Generation ✶ New V2
Agent reads every acceptance criterion and generates corresponding tests: happy paths, error states, edge cases from spec, regression coverage from project memory. Tests committed to GitHub test branch.
If the project uses multiple frameworks (Jest + Cypress), detection accuracy is unvalidated.
M1 Developer Reviews Generated Test Suite + AC Mapping ✶ Evaluator
Developer Read / Analysis Slack · GitHub · Cursor/IDE
Developer reviews the AC-to-test mapping — are the generated tests actually testing what the AC requires? Flags incorrect mappings through a structured disagreement flow.
Job: Verify that generated tests test what was specified — not just that they exist.
No structured workflow exists for developer test rejection (X11).
System event — Pass 1: Structural Checks (Cheap Model) ✶ Evaluator
Validates test suite structure without executing. Checks: every AC has at least one test, every test has AC mapping, no orphaned tests, file structure matches conventions. Output: structural coverage score (0–100) and gap list.
What structural gap severity triggers a block on Pass 2? Orphaned test vs. missing AC are different severities.
M2 Developer Fixes Failures — Code Error vs. Test Error
Developer Read → Write / Mutation Cursor/IDE · GitHub
Developer distinguishes between: (a) implementation gap — code doesn’t meet AC, (b) test error — generated test is wrong, (c) ambiguous. Sokuvo maps each failure to its AC and surfaces spec context in the IDE sidebar.
Job: Fix the right thing — not waste time on test infrastructure when the problem is an implementation gap.
M3 Eng Lead Reviews Pass 1 Structural Results ✶ Evaluator
Eng Lead Read / Analysis → Gate Web dashboard · Slack
Reviews which ACs have no test, which tests have no AC mapping, orphaned test files. Makes a go/no-go decision for Pass 2.
Job: Catch structural test gaps before the expensive functional evaluation.
System event — Pass 2: Functional Correctness (Balanced Model) ✶ Evaluator
Executes the full test suite. Checks for silent passes — tests that pass but don’t validate the AC they claim to cover. Classifies each failure as: implementation gap, test error, or ambiguous. Output: functional coverage score and classified failure list.
Detecting silent passes requires reasoning about what assertions verify. False negatives are the highest-risk failure mode.
M4 Developer Reviews Pass 2 Classified Failures ✶ Evaluator
Developer Read → Write / Mutation Cursor/IDE · GitHub
Each failure typed as implementation gap, test error, or ambiguous. Developer addresses implementation gaps (code fixes) and test errors (test corrections) separately.
Job: Know which failures are your code and which are the test — fix the right thing.
System event — Pass 3: Adversarial Review (Frontier, Conditional) ✶ Evaluator
Probes for edge cases the test suite didn’t cover and silent failures. Uses a different model family to reduce sycophantic confirmation. Results delivered to Eng Lead only — not developer.
Three undefined trigger conditions: (1) what failure count triggers automatic run, (2) can Eng Lead trigger manually, (3) cost threshold (X10).
M5 Eng Lead Reviews Pass 3 Adversarial Findings ✶ Evaluator
Eng Lead Read / Analysis Web dashboard · Slack
Reviews silent failure candidates — behaviors that pass all tests but may violate spec intent. Classifies each as real risk, acceptable, or needs PM escalation.
Job: Find failures tests don’t catch — the ones that reach production and damage trust.
M6 Eng Lead Reviews Consolidated Multi-Pass Report
Eng Lead Read / Analysis Web dashboard · Slack
Consolidated report: Pass 1 structural + Pass 2 functional + Pass 3 adversarial (if run). Findings de-duplicated. Each item has a recommended action. Identifies items for PM escalation.
Job: See the full picture in one place — not reconcile three separate reports.
M7 Eng Lead Escalates Edge Cases to PM
Eng Lead → PM Write / Mutation Slack · Web dashboard
Product decisions, not technical ones: AC ambiguity, intended behavior that looks like a bug, scope questions. Escalates with full context per item — three decision options (change AC / accept / backlog).
Job: Give the PM a specific decision — not a raw test failure without context.
M8 PM Decides on Edge Cases + Reviews AC Coverage
PM Read → Write / Mutation Slack · Web dashboard
Two inputs: (1) edge case decisions — change AC, accept, or backlog, (2) AC coverage report in plain language — pass/fail per criterion, not stack traces. PM makes explicit decisions per escalated item.
Job: Make deliberate product decisions on edge cases. Know whether the feature works as specified.
System event — Edge Case Decision Persistence
PM decisions written to: (1) spec AC updated in Confluence if changed, (2) project memory with reasoning, (3) test stage audit trail. Developer notified of changed ACs.
M9 Eng Lead Technical Sign-Off on Test Results
Eng Lead Gate Web dashboard · Slack
All passes complete, all findings resolved, PM decisions captured. Eng Lead makes explicit technical sign-off — a deliberate quality decision, not a checkbox.
Job: Own the quality decision that test results are sufficient — not just confirm CI is green.
Gate — Test Gate ✶ New V2
Five conditions: (1) structural gaps resolved, (2) functional failures classified and addressed, (3) adversarial findings reviewed, (4) PM edge case decisions captured, (5) both sign-offs recorded. First failed condition blocks with specific reason. Gate cannot self-clear.
System event — Test → Review Stage Transition
All five gate conditions met. Sokuvo begins auto-assembling the review package: maps every merged PR to spec ACs, generates annotated diffs, creates traceability links. Trust classification evaluator scores every output.

Ship stage

The most backstage-heavy stage. Three consecutive system events before any human action. PM deploy approval is the only irreversible action in the entire delivery chain.

→
Ship is where traceability pays off. The changelog, merge PR, and deploy cascade are all generated from the delivery record. For the grid view, see Service Blueprint (05f).
System event — Final Evaluator Gate Check ✶ Evaluator
final_eval_checker reads: all stage gate pass records, audit trail completeness (no gaps), open blocker count (must be zero), artifact inventory (all required artifacts present). Blocks with specific reason if any condition fails.
If the eval finds an incomplete audit trail entry from Build, does Ship block automatically or does the PM override?
System event — Changelog Generation
Compiled from: accepted ACs (Define), architecture decisions (Build), edge case decisions (Test), approved release notes (Review). Two versions: technical and customer-facing. Published to Confluence as draft.
Changelog quality depends on Build decision capture. Decisions made outside Sokuvo channels are not in the changelog (X12).
System event — Merge PR Creation
create_pull_request (planned — not yet in V1): reads feature branch, spec, and project memory. PR description: spec goals summary, AC closure checklist, decision log, audit trail link.
This is a planned capability not yet in V1 — Ship depends on it.
M4 Eng Lead Reviews Changelog + Merge PR
Eng Lead Read → Write / Mutation Confluence · GitHub · Slack
Reviews changelog for accuracy — are all architecture decisions represented? Decisions made outside Sokuvo that are missing? Can edit sections inline before approving.
Job: Approve a changelog that reflects what was built and decided — not one that omits half the decisions.
No diff exists between agent output and actual decisions. Eng Lead must know what was decided to spot errors (X12).
M5 PM Reviews Ship Summary
PM Read / Analysis Web dashboard · Slack
Deploy package: every shipped AC, accepted out-of-scope items, deferred backlog, approved release notes. PM reviews before the deploy decision.
Job: Know exactly what is in this release and what is not.
M6 PM Approves Deploy — The Only Irreversible Action ⚠ Irreversible
PM Write / Mutation (irreversible) Web dashboard · Slack
The only action in the entire delivery chain that cannot be undone. On approval, the cascade fires: deploy pipeline, Jira closures, developer notifications, audit trail entry. PM sees exactly what will happen.
Job: Make the deploy decision with full information — knowing exactly what will happen and to whom.
Gate — Ship Deploy Gate
PM approval fires the cascade: (1) deployment pipeline (planned), (2) jira_update batch — all tickets to Done, (3) per-developer closure notification, (4) Eng Lead confirmation, (5) audit trail entry.
Deploy pipeline trigger depends on CI/CD integration not yet built in V1.
System event — Deploy Cascade
Deployment pipeline fires. All Jira tickets transition to Done. Per-developer closure notifications sent. Eng Lead receives confirmation. Audit trail sealed.
M8 Developer Receives Closure Signal
Developer Read / Analysis (notification) Slack · Jira
Each developer receives a closure notification: tickets closed, feature shipped, contribution summary. Automatic — part of the deploy cascade.
Job: Know your work shipped — without checking Jira or asking in Slack.
If something is wrong at Ship, no mechanism to notify the developer specifically.
System event — Project Archival
Project marked archived. Audit trail sealed (immutable). Context graph preserved in project memory for future queries.
Relevance filtering for archived project context in future queries is undefined.
