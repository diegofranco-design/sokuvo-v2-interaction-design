01 — JTBD × Conversation Design
Why conversational design
is different

Visual UI design organises space. Conversational design organises time. The mental models, tools, and artefacts are different.

The core difference

Visual UI
Organises space
User navigates between screens
Interface waits
Sitemap = hierarchy of pages
Wireframe = layout of a screen
Conversational UI (Sokuvo)
Organises time and state
User expresses intent in natural language
System responds in turns
Conversation map = graph of states
Message anatomy = structure of a turn

The four artefacts and what they answer

01
Jobs to be Done
Answers: What is the user trying to accomplish and why?
Maps motivation across six stages and three roles. The continuity job is unique to Sokuvo — one actor's output is always the next actor's input.
02
Mental Model Flows
Answers: How does the system behave for each interaction type?
Three patterns (Read/Analysis, Artifact Generation, Write/Mutation) with happy paths and error maps. The system perspective, not the user perspective.
03
Artifact State Model
Answers: What states can an artifact be in, and what can the user do in each?
Seven states (generating, draft, iterating, pending_approval, published, archived, blocked) with explicit transition rules and ownership boundaries.
04
Conversation Map
Answers: What does the user see turn by turn, and how do multiple roles coordinate?
Three roles in parallel, showing what each actor sees at each moment, how the system responds, and where coordination events connect the roles.

The new V2 actor: the evaluator

V2 introduces a fourth actor in the Define stage: the spec evaluator. It is not a user, not a conversational agent, and not a system step — it is an automated quality layer that produces a score, identifies gaps, and controls a gate.

The evaluator raises design questions that do not exist in V1: How does the PM experience a blocked state caused by an automated score? How does the Eng Lead calibrate annotation depth based on a score they did not produce? How does the Developer know which evaluator gaps are worth their attention? These questions are the open questions in section 05.

04 — Artifact State Model
What can be done
depends on what state
something is in

Every artifact Sokuvo generates passes through a defined lifecycle. The state model establishes the canonical vocabulary, the transition rules, the ownership boundaries, and the open questions that every surface must answer before wireframing begins.

→
The state model is a prerequisite for the conversation map and the service blueprint. Without it, you cannot answer: what actions are available here? Who owns this object? What happens if the user navigates away? These questions are answered by state, not by screen.

Why a state model

Sokuvo generates artifacts — PRDs, epics, user stories, documentation — that exist across multiple surfaces and pass through multiple hands. Without a shared vocabulary for what state an artifact is in, each surface invents its own labels ("In progress," "Under review," "Done"), and the actions available to users become unpredictable.

The state model defines the seven canonical states, the seventeen transitions between them, who can trigger each transition, which bounded context owns the artifact in each state, and what design principles govern every state-aware interaction.

The seven states

`generating` Bounded context: Sokuvo
What it is
The system is producing the artifact section by section. The artifact does not yet exist as an editable object.
Surface
Slack (waiting state + stage labels) or Web editor (section-by-section stream with skeleton placeholders)
Actor
System
What the user can do
Watch generation progress only — cannot edit, publish, or cancel mid-stream.
`draft` Bounded context: Sokuvo
What it is
Generation is complete. The artifact exists as an editable object owned by Sokuvo. Not committed to any record system. Gaps are labeled, sources are cited.
Surface
Slack (inline, collapsed, with expand action) or Web editor (full split-view with TOC + sources panel)
Actor
PM · Eng Lead · Developer
What the user can do
Edit inline · Regenerate a section (diff preview) · Mark a gap · Copy · Export as .docx · Publish · Discard
`iterating` Bounded context: Sokuvo
What it is
The user requested a revision. The system is regenerating targeted sections while preserving the rest. Artifact remains owned by Sokuvo.
Surface
Web editor — targeted section regenerates inline with diff preview (new vs. prior). User accepts or rejects before state returns to draft.
Actor
System (executing)
What the user can do
Accept the regenerated version · Keep the prior edit — cannot publish while a section is regenerating.
Open question — Multi-cycle version control is undefined. If the user regenerates → edits → regenerates again, is the original draft recoverable? This must be resolved before the iteration UX is fully designed.
`pending_approval` Bounded context: Both — boundary state
What it is
The user has clicked Publish. The system has prepared the Confluence write and is waiting for explicit gate approval before committing. This is the boundary between the Artifact Generation and Write/Mutation patterns.
Surface
Web editor (publish gate modal with full preview) or Slack (preview card with Approve / Edit / Cancel)
Actor
PM · Eng Lead (not developers)
What the user can do
Approve the write · Edit fields before committing · Cancel (returns to draft cleanly — no half-committed state). Silence is never approval.
`published` Bounded context: Record system — Confluence owns it
What it is
The artifact has been successfully written to Confluence. Carries Sokuvo provenance metadata: "Generated by Sokuvo" footer, traced-from links, bidirectional traceability. The Sokuvo draft is no longer the canonical version.
Surface
Confluence is the destination. Slack and Web show a receipt card with a deep-link to the published page.
Actor
System + PM (who approved)
What the user can do
Open in Confluence · View in Sokuvo editor (read-only) · Request a new version (creates a new draft — does not overwrite the published page)
`archived` Bounded context: Sokuvo
What it is
The artifact is no longer active — project archived, superseded, or explicitly discarded. Preserved for audit trail but not surfaced in active views.
Surface
Not surfaced in active views. Accessible via audit trail or admin panel only.
Actor
PM (explicit discard) · System (project archival)
What the user can do
Restore to draft (if not yet published) · View version history
`blocked` Bounded context: Sokuvo
What it is
Generation or publish failed and cannot proceed automatically. Causes: empty retrieval, Confluence write failure, permission error, or quality floor breach where all critical sections are flagged as sparse.
Surface
Web editor or Slack — specific error shown, never a generic failure message. The error must carry enough information for the user to know what to do next.
Actor
System (failure detected)
What the user can do
Provide missing sources and retry · Resolve the permission issue · Retry the write · Accept gaps and override the quality floor
Open question — The quality floor threshold is undefined — the system cannot determine when sparse gaps are severe enough to block vs. warn. This state may be incorrectly triggered or never triggered until the threshold is specified.

Design principles

The artifact is always in exactly one state
No state overlaps. generating and draft are sequential. iterating always resolves back to draft. An artifact that is published is not also draft. The state model is exhaustive and mutually exclusive.
Sokuvo owns the artifact until it is published
In generating, draft, iterating, pending_approval, and blocked — the artifact belongs to Sokuvo. Only on published does ownership transfer to the record system. This determines which surface is the canonical source of truth at each state.
Publish is a bounded context crossing, not a button
Moving from pending_approval to published changes the artifact's nature — from a Sokuvo draft to a Confluence record with a different owner, different edit surface, and different traceability model. That crossing must be explicit in the UI, not silent.
Silence is never approval — applies to publish too
The same principle that governs Write/Mutation previews applies to the publish gate. The system waits for an explicit approval signal. The pending_approval state holds the artifact at the boundary until that signal arrives.
Blocked is an honest state, not a generic error
When the artifact cannot proceed, the system names the specific reason — empty retrieval, permission failure, quality floor breach. A generic "something went wrong" message is a failure of the honesty principle.
Published does not mean frozen
The user can request a new version after publishing. This creates a new draft — it does not overwrite the published Confluence page. The Sokuvo editor reflects Sokuvo's version history; Confluence reflects what was committed.

Open questions

OQ1Quality floor thresholdBlocks blocked state design
How many sparse sections make an artifact too broken to publish? Options: (a) Fixed count — more than N critical sections sparse; (b) Ratio — more than 50% of sections sparse; (c) Section-weight model — sparse Goals or Acceptance Criteria blocks publish; sparse Open Questions does not.
OQ2Multi-cycle version controlBlocks iterating state UX
What is the full undo model across multiple iteration cycles? The diff preview handles one regeneration cycle. If the user regenerates → edits → regenerates again, the current model is silent on whether prior states are recoverable.
OQ3Confluence versioningBlocks Write/Mutation flow
Does publishing always create a new Confluence page, or can it update an existing one? Currently confluence_create only creates. If the PM publishes a PRD, edits it in Confluence, then re-generates in Sokuvo — two Confluence pages exist for the same artifact.
OQ4Ownership after publishBlocks Web editor design
After publish, who owns the artifact — Sokuvo or Confluence? If someone edits the Confluence page directly, does Sokuvo know? This requires either a sync mechanism or an explicit out-of-sync signal in the Sokuvo editor.
OQ5Continuity job — handoff signalHighest — blocks all stage transitions
What signal does the next actor receive when an artifact is published? Does the Eng Lead receive a Slack notification? Does it appear in their morning_report? Is there a named handoff event? This is the Define → Plan stage transition and currently has no designed surface.
05 — How to read the blueprint
Six rows.
Time runs left.
The gap is the point.

The service blueprints on the following pages use a consistent format. This page explains the format, what each row means, and what to look for when reading them.

The six rows

PM
What the Project Manager sees and does at each moment. Actions here are product decisions — scope, approval, prioritisation.
Eng Lead
What the Engineering Lead sees and does. Actions here are technical decisions — architecture, feasibility, code quality sign-off.
Developer
What the Developer sees and does. Actions here are implementation decisions — code, tests, PR creation, feedback response.
Line of visibility
The boundary between what users see and what the system does. Everything above this line is interaction design. Everything below is system design. When a column has no cells above the line, that moment is fully automated — no human action required or visible.
Sokuvo backstage
What Sokuvo does internally at each moment — retrieval, evaluation, routing, writing to external systems. Invisible to users unless explicitly surfaced. Click any backstage cell for full detail.
Surface
Which tool or platform carries this moment. Slack Web Cursor/IDE Jira GitHub Auto

What to look for

Consecutive empty actor rows
When multiple columns in a row have no cell — no actor action — the system is running fully on its own for several consecutive moments. This is an automation promise. Validate that users are comfortable with that level of agency before committing to it.
Cells marked with ⚠ gap
A capability gap — a job the user needs done that has no current Sokuvo workflow. These are product backlog items, not design decisions. They represent features that must be built before the interaction can be designed.
Open questions in the detail panel
Every cell with an open question is a design decision that cannot be resolved without input from product, engineering, or the business. These are the agenda items for the team session — not things to resolve by assumption.
The same gap across multiple stages
When you see the same open question appear in the same structural position across Define, Plan, Build, Test, Review, and Ship — that is a system design problem, not a stage design problem. The Engineering Lead approval surface gap appears in all six stages of Sokuvo V2. That pattern is the most important finding in the entire blueprint.
Green moments — evaluator layer
Moments with a green header are driven by the automated evaluation layer — spec evaluator, plan evaluator, multi-pass test evaluator, trust classifier. These are new in V2 and represent the biggest design surface that does not yet exist in V1.

Reading sequence

For team sessions, read the blueprints in two passes. First pass: read each row horizontally — what is the pattern for this actor across the full stage? Where are they active, where are they passive, where are they waiting? Second pass: read each column vertically — at this specific moment, what is every actor doing simultaneously? What surface does it happen on? What is the system doing backstage?

Click any cell or backstage node to see the full detail — what the actor sees, what Sokuvo does, which surface it happens on, what job it serves, and any open question tied to that moment.
